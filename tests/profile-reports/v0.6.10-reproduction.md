## Decision

The event-loop experiment materially reduces idle CPU, but the complete v0.6.10 targets are not met. The event-loop remains opt-in until CPU reproducibility is confirmed under a longer sample and active animation is measured separately. No version promotion, commit, tag, or push is made.

## Next work

1. Measure active animation with the selected session actually running an AI-like command.
2. Separate external observer time from launcher completion time in key/switch/archive/restore metrics.
3. Optimize restore pane creation/layout only after the internal and external measurements agree.
4. Re-run the full target matrix before changing the default event-loop setting.

## Frame/render CPU analysis

With metrics enabled, the active reproduction recorded 136 animation frames over approximately 34 seconds. The frame path consumed 298ms total (about 2.19ms/frame), including 139ms for name formatting and 40ms for ANSI emission. Four full renders consumed 105ms and two state-change renders consumed 4.8ms.

The no-animation control measured active CPU 5.38%, while the instrumented animation run measured 6.96% (the latter includes measurement overhead). Since disabling animation did not remove the active CPU excess, frame/name formatting/ANSI emission is not the primary cause. The next measurement boundary is maintenance/read/refresh, especially the selected-session state collection and external observer calls.

## Candidate optimization checks

Additional candidates were measured but not retained. Suppressing unchanged waiting-state fingerprint capture produced active CPU 5.49%, recent-activity suppression produced 5.68%, and increasing state refresh to 10 seconds produced active CPU 9.29% with key latency 72ms. These results do not establish a safe improvement, so the production behavior remains unchanged. The next required split is the maintenance tick itself: read wait, age rendering, force-refresh option lookup, and target state collection.

The maintenance instrumentation recorded 142 loop iterations in about 35 seconds: 140 read timeouts, 42 age renders totaling 107.9ms, 8 force-refresh checks totaling 148.0ms, and 42 state-refresh checks (40 skipped) totaling 886.0ms. Read time is wall wait and must not be treated as CPU time. An all-animation blocking-read experiment produced active CPU 0% but failed navigation observer and resize invariants, so it was reverted.
